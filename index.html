Do dado repetido ao banco organizado

Da 1FN à 5FN, e até a hora de quebrar as regras de propósito: um passeio com exemplos de quiz, SQL e vídeos para você ir mais longe.

Autores: João Victor Guimarães Gomes, Matheus Augusto Antunes Pentogennis, Gustavo Gabriel Naves Ferreira, Lucas Siqueira Teles, Lucas da Graça Leandro e Gabriel Gonçalves Lima Revisado em: 16/10/2026
Antes de começar: os nomes, produtos, valores e registros usados nos exemplos são totalmente fictícios. Não representam pessoas, clientes ou empresas reais.

Imagine que um sistema de quiz guarde as perguntas, a categoria, o nome de quem publicou e o endereço da fonte tudo em uma única tabela. No começo parece prático, mas, quando o sistema cresce, fica fácil repetir dados e cometer erros. A normalização é uma forma de organizar essas informações em tabelas que se relacionam de maneira mais clara.

Vamos por uma trilha em três partes. Em cada uma você encontra um exemplo, um trecho de SQL e vídeos para quem quiser ir além do texto.

01 · O PROBLEMA

Quando tudo fica em uma tabela só

O problema não é ter poucas linhas. É que os dados da fonte se repetem em cada pergunta que a usa. Se o nome da fonte mudar, será preciso atualizar várias linhas.

A

Anomalia de atualização

O nome de uma fonte é alterado em uma linha, mas esquecido em outra. O banco passa a ter versões diferentes da mesma informação.

B

Anomalia de inserção

Não dá para cadastrar uma fonte antes de existir uma pergunta que a use, se tudo estiver preso na mesma tabela.

C

Anomalia de exclusão

Ao apagar a última pergunta de uma fonte, podemos perder também os dados dessa fonte.

02 · PARTE 1 · 1FN, 2FN E 3FN

Separando o que está misturado

1FN

Primeira Forma Normal: valores atômicos

Cada campo guarda um único valor, e não uma lista dentro da mesma célula. Por exemplo, não guardar "Certo; Errado" no campo de alternativas. Cada alternativa deve ter seu próprio registro relacionado à pergunta.

2FN

Segunda Forma Normal: sem dependência parcial

A tabela está na 1FN e cada atributo fora da chave depende da chave inteira, não só de um pedaço dela. Isso importa quando a chave primária é composta por duas ou mais colunas.

Neste exemplo, as tabelas principais usam identificadores simples. Por isso não existe dependência parcial nelas; ainda assim, vale conhecer a regra.

3FN

Terceira Forma Normal: sem dependência transitiva

A tabela está na 2FN e atributos fora da chave não determinam outros atributos que deveriam morar em outra tabela. O identificador da fonte determina o nome e a URL dela; esses dados ficam em fontes, e a pergunta guarda só a referência.

03 · PARTE 2 · BCNF, 4FN E 5FN

Quando a 3FN ainda deixa redundância

A 3FN resolve a maioria dos casos, mas ainda sobra redundância em dois tipos de situação: quando um atributo que não é chave determina outro (BCNF) e quando existem listas independentes na mesma tabela (4FN e 5FN).

BCNF: todo determinante precisa ser chave

Na forma normal de Boyce-Codd, sempre que A → B, A tem de ser uma chave. Nosso exemplo: cada moderador cuida de uma única categoria (moderador → categoria), mas o moderador não é chave da tabela abaixo.

Rodadas do quiz. Chaves candidatas: (jogador, categoria) e (jogador, moderador)
JogadorCategoriaModerador
AnaWebMarcos
BiaWebMarcos
AnaBanco de DadosSílvia

Repare que "Marcos cuida de Web" aparece duas vezes. A tabela está na 3FN (categoria faz parte de uma chave candidata), mas viola a BCNF. A solução é separar: uma tabela moderador (moderador, categoria) e uma tabela rodada (jogador, moderador).

Limite honesto: depois da decomposição, o banco deixa de garantir sozinho que (jogador, categoria) determine um único moderador. Nem sempre dá para atingir a BCNF preservando todas as dependências.

4FN: fatos independentes, tabelas independentes

Uma dependência multivalorada (A ↠ B) aparece quando A tem um conjunto de valores de B, independente das outras colunas. Se a pergunta fact-001 tem as tags http e web e está traduzida em pt e en, uma tabela única precisaria de 4 linhas, uma para cada combinação. Na 4FN separamos em pergunta_tag (2 linhas) e pergunta_idioma (2 linhas). Com 5 tags e 3 idiomas, seriam 15 linhas contra 8.

5FN: quando só o JOIN reconstrói a tabela

Uma dependência de junção existe quando uma tabela pode ser quebrada em três ou mais partes e reconstruída sem perda apenas juntando todas elas. É raro e só aparece quando uma regra do negócio combina três coisas ao mesmo tempo. Na prática, a maioria dos projetos para na 3FN ou na BCNF, olhando a 4FN quando há listas independentes.

Aprofundamento: definições formais

BCNF: para toda dependência funcional não trivial X → Y, X é superchave. 4FN: está na BCNF e, para toda dependência multivalorada não trivial X ↠ Y, X é superchave (Fagin, 1977). 5FN: está na 4FN e toda dependência de junção é implicada pelas chaves candidatas. Uma decomposição deve ser sem perdas (o JOIN devolve exatamente a tabela original).

04 · PARTE 3 · DESNORMALIZAÇÃO

Quando repetir dados vale a pena

Normalizar não é sempre o objetivo final. Cada tabela nova pede um JOIN, e em relatórios com milhões de linhas isso custa tempo. A desnormalização é repetir dados de propósito, de forma controlada, para deixar certas leituras mais rápidas.

Dois jeitos de usar o banco
CaracterísticaTransacional (OLTP)Analítico (OLAP)
Uso típicoResponder perguntas e gravar respostas do quizRelatórios e painéis sobre o histórico
Operação mais comumMuitas escritas pequenasPoucas leituras enormes
ModeloNormalizado (3FN)Esquema estrela, com dados repetidos

Um caminho seguro é manter as tabelas normalizadas e criar uma visão materializada, que guarda o resultado pronto de uma consulta. Aqui, um resumo de perguntas por categoria:

CREATE MATERIALIZED VIEW resumo_categoria AS
SELECT c.nome AS categoria, COUNT(p.id_pergunta) AS total_perguntas
FROM categorias c
LEFT JOIN perguntas p ON p.id_categoria = c.id_categoria
GROUP BY c.id_categoria, c.nome;

-- O resumo não se atualiza sozinho: depois de mudar os dados, é preciso renovar.
REFRESH MATERIALIZED VIEW resumo_categoria;

Cuidados: o dado repetido pode ficar desatualizado (por isso o REFRESH), as escritas ficam mais caras e o esquema mais difícil de manter. Antes de desnormalizar, meça: compare a consulta com EXPLAIN ANALYZE nas duas versões e use índices primeiro.

06 · SQL NA PRÁTICA

Separando os dados com PostgreSQL

Os scripts completos estão em sql/normalizacao.sql (1FN a 3FN) e sql/normalizacao-avancada.sql (BCNF, 4FN e visão materializada). A ideia principal: categoria fica em uma tabela, fonte em outra e a pergunta aponta para elas por chaves estrangeiras.

CREATE TABLE categorias (
    id_categoria INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    nome VARCHAR(80) NOT NULL UNIQUE
);

CREATE TABLE fontes (
    id_fonte INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    nome VARCHAR(100) NOT NULL,
    url VARCHAR(250) NOT NULL UNIQUE
);

CREATE TABLE perguntas (
    id_pergunta INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    enunciado TEXT NOT NULL,
    resposta_correta BOOLEAN NOT NULL,
    id_categoria INTEGER NOT NULL REFERENCES categorias(id_categoria),
    id_fonte INTEGER NOT NULL REFERENCES fontes(id_fonte)
);

O nome da categoria e os dados da fonte não se repetem dentro de cada pergunta. Os campos id_categoria e id_fonte fazem a ligação.

Consulta com JOIN

SELECT p.id_pergunta, p.enunciado, c.nome AS categoria,
       f.nome AS fonte
FROM perguntas p
JOIN categorias c ON c.id_categoria = p.id_categoria
JOIN fontes f ON f.id_fonte = p.id_fonte
ORDER BY p.id_pergunta;

O JOIN reúne as informações para exibir o resultado. Normalizar não significa perder informação: significa guardá-la de forma organizada e juntar os dados quando necessário.

Como testar: abra o pgAdmin, selecione um banco de testes PostgreSQL vazio, abra o Query Tool e execute o arquivo. Os scripts apagam apenas as tabelas de exemplo com esses nomes no banco selecionado.

07 · LIMITES E CUIDADOS

Normalizar resolve tudo?

Não. A normalização reduz redundância e anomalias, mas não substitui regras de negócio, validações, índices ou cuidados com segurança. Também é preciso pensar nas consultas que o sistema vai executar. Um banco bem modelado precisa ser consistente e atender ao uso real da aplicação.

Outro cuidado é não criar tabelas separadas sem necessidade: a divisão deve representar dependências reais entre os dados. E "sempre normalize até a 3FN" não é regra, é ponto de partida que depende do contexto.
